# T5 — SensorReport TX via LXMF (control wire + control path): evidence

**Ticket:** T5 (#163). **Accept:** the leaf's sensor readings are transmitted in
an LMAO `SensorReport` wrapped in the top-level `LMAOEnvelope` (proto
`lma_messages.proto` field 10), packed into an LXMF message signed by the leaf
identity and addressed to the `lxmf/delivery` DEST (design §4; proto
Title="p:Envelope"), and a report "lands" in the server's DuckDB pipeline like
the C/MicroPython clients.

## Result: HOST PASS (control wire + control path) · live E2E-to-DuckDB PENDING-HARDWARE

The design §6b decision — **protobuf-generated from the single shared schema,
not a hand-written second encoder** — is implemented and proven: `crates/lma-wire`
uses **prost-build to generate `LmaoEnvelope`/`SensorReport` directly from
`proto/lma_messages.proto`**, and the generated bytes are **cross-language-verified
byte-for-byte against the Python reference encoder**
(`cardputer_client/proto/lma_encoder.py`). `crates/lma-lxmf` packs that envelope
into a signed LXMF message addressed to the `lxmf/delivery` DEST and verifies on
receipt. Transmitting the report live over radio to the server's DuckDB sink is
the on-device hardware leg (E2E; pairs with T6).

## `crates/lma-wire` (design §5 `lma-wire`) — prost from the shared .proto (§6b DRY)

- `build.rs` runs **prost-build** against the shared `proto/lma_messages.proto`
  (the single schema, generated everywhere). Needs `protoc` at build time:
  `export PROTOC=/path/to/protoc` (pinned in the T0 era:
  `/tmp/protoc-27.3/bin/protoc`, official aarch64 build).
- Generated types surfaced as `lma_wire::{LmaoEnvelope, SensorReport,
  SensorReading}` plus helpers `sensor_envelope(…)` / `reading(…)`.
- 3 tests via `bazel run //rust-client:test_lma_wire`:
  - `sensor_report_serializes_identically_to_python_reference` — prost
    `SensorReport` bytes === Python `encode_sensor_report` goldens.
  - `envelope_serializes_identically_to_python_reference` — prost
    `LmaoEnvelope` (field-10 sensor wrapper) bytes === Python
    `encode_sensor_envelope` goldens.
  - `roundtrip_report_decode_matches` — decode → identical fields.
- This is the anti-drift lock: a proto change must be mirrored in `lma_encoder.py`
  on pain of the golden-vector tests failing.

## `crates/lma-lxmf` — LXMF control path (pack + sign + verify)

- `pack_envelope(identity, dest, timestamp, envelope)` → packs the prost
  envelope as the LXMF `Content`, Title=`"p:Envelope"`, signs with the leaf
  identity's Ed25519 key (source hash = `identity.hash()`), addressed to the
  `lxmf/delivery` DEST.
- `unpack_envelope_verified(packed, source)` → unpacks, verifies the signature
  against the source identity, checks the Title, decodes the envelope.
- 2 tests via `bazel run //rust-client:test_lma_lxmf`:
  - `pack_sign_unpack_verify_roundtrip` — pack → verify (valid), src/dst hashes
    correct, content decodes to the exact `SensorReport`, and the re-encoded
    envelope byte-matches the Python `lma_encoder` goldens.
  - `tampered_content_rejects_signature` — a flipped content byte fails
    signature verification (`SignError`).
- Deps on the pinned `lxmf-core 0.1.5` + `rns-crypto 0.1.10` (SHA-256 matched
  the `rust-client/UPSTREAM.md` / `repositories.bzl` pins) and `lma-identity`
  (delivery DEST).

## Build note (protoc)
`lma-wire`'s `build.rs` needs `protoc`. Both test shims fail fast with a clear
message if none is on `PATH` or via `PROTOC`. In CI pass
`PROTOC=/path/to/protoc` (version pinned to what `proto/` was generated with).

## On-device hardware leg (held)
Radio-transmitting the signed LXMF `SensorReport` to the server's DuckDB sink
(live E2E, §T5 accept) is production-gated hardware, per the standing mandate:
MicroPython Cardputer stays untouched until the Rust client is E2E. The control
wire + control path are the host-testable precondition; transport (T6
Resource-over-Link) carries it over the radio.
